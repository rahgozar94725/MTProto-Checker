This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Single source of truth for this repo. `AGENTS.md` is a pointer to this file.

## Commands

```bash
go run .                          # dev server on 127.0.0.1:3000 (PORT/HOST env override)
go build -o mtproto-checker .     # single self-contained binary
go test ./... -short              # unit tests only — skips network/proxy-file tests
go test ./... -v                  # full run, incl. live Telegram handshake tests
go test -run TestDecodeSecret -v  # single test
go test -bench BenchmarkBatchPipeline -benchtime=1x
go vet ./...                      # clean as of last run

# reproduce a release build locally
GOOS=linux GOARCH=arm64 CGO_ENABLED=0 go build -ldflags="-X main.version=v0.0.0-local" -o /tmp/mtc .

# rebuild the proxy snapshot by hand — fetches all 17 sources, needs network, no npm install
node scripts/build-snapshot.mjs /tmp/snapshot.txt

# re-record scripts/snapshot-baseline.json after reviewing why a source's volume moved
node scripts/build-snapshot.mjs /tmp/snapshot.txt --write-baseline
```

Frontend tests (Node ≥ 22, `npm install` first — nothing in production runs on Node):

```bash
npm test                          # alias for test:unit
npm run test:unit                 # node:test + jsdom over tests/unit/**/*.test.js
npm run test:watch                # same, in watch mode
npm run test:coverage             # adds --experimental-test-coverage over public/js/**
npm run test:coverage:ci          # same, minus app.js, gated at 100% lines and branches
npm run test:e2e                  # Playwright, boots `go run .` itself
npm run test:all                  # unit then e2e
npx playwright install chromium   # one-time, before the first e2e run
E2E_LIVE=1 npm run test:e2e       # also runs the live smoke test against real Telegram
```

`node --test` is given a **quoted glob**, not a directory — Node resolves a bare directory as a module and dies with `MODULE_NOT_FOUND`. Coverage is still behind `--experimental-test-coverage` as of Node 26.5.0.

`test:coverage:ci` is the enforcement behind the 100% claims below; `test:coverage` stays ungated for local reading. The gate excludes `public/js/app.js` (its ~35% is the cache-busted-mount artifact described under **Frontend tests**, not a real gap) and does not gate *functions*, deliberately and permanently: the only misses are timer callbacks, which run or not depending on how long a test after them happens to take. `render.js` is the standing example — `showToast()`'s own `setTimeout` callback kept it at 85.71%, then 87.50% as the file grew, and reads 100% as of 2026-08-10. Read any function figure here as a measurement, never as a gate. The callback's *lines* are a different matter and are gated: `render.test.js` outwaits `TOAST_MS` on purpose, because leaving them to whichever sibling test happens to run long enough would make a 100% line gate a function of wall-clock. `--test-coverage-lines`/`-branches` need Node ≥ 22.8.

A host build (`go1.26.4 windows/amd64`) produces a 22,624,768-byte (~21.6 MiB) binary with `public/` baked in. Only `public/` is embedded — `package.json`, `node_modules/` and `tests/` sit outside it and never reach the binary; `tests/unit/harness.test.js` is the permanent guard on that. **Amendment:** the guard's allowlist is code and assets (`.html`, `.css`, `.js`, `.woff2`, `.png`, `.svg`, `.ico`) **plus `public/data/*.txt` and nothing broader** — one deliberate data file, the proxy snapshot. A `.txt` elsewhere under `public/`, or a non-`.txt` under `public/data/`, is still an offender, and the allowlist predicate is unit-tested against those exact cases rather than only against the current tree.

**Formatting:** `.gitattributes` pins `*.go` (and all text files) to LF in the repository *and* the working copy, so `gofmt -l .` is meaningful on every platform and is expected to be clean. Caveat: a checkout that predates `.gitattributes` may still hold stale CRLF working copies (`git ls-files --eol` shows `w/crlf`), which makes `gofmt -l` flag every Go file on line endings alone — fix with `rm <files> && git checkout -- <files>`, not by re-formatting.

No linter, no formatter config. Three workflows:

- `.github/workflows/test.yml` — on every `push` and `pull_request`, three jobs: `js` (Node 22, `npm ci`, `npm test`, then `npm run test:coverage:ci` as the coverage gate), `go` (`go vet`, `go test ./... -short`, the same run again under `-race` as its own step so a data race is distinguishable from an ordinary failure, and a `gofmt -l .` gate that has to test the file list itself because `gofmt -l` exits 0 even with offenders — note `-short` only drives `/fetch-sources`' shared slice, client and byte budget plus `checkproxy_test.go`'s handshake; `/check-stream`'s per-proxy goroutines and `dnsCache` sit behind the tests it skips), `e2e` (both toolchains, `~/.cache/ms-playwright` cached on `package-lock.json`, report uploaded on failure). `E2E_LIVE` is never set in CI. Its `push` trigger carries `branches-ignore: [snapshot]`, without which every nightly bot commit would run the whole matrix over a branch that holds one text file and no code.
- `.github/workflows/snapshot.yml` — the nightly rebuild: `schedule` at `17 3 * * *` (off the hour, where GitHub's scheduler is least contended) plus `workflow_dispatch`, and `contents: write` **on the job rather than the workflow**, so a job added later does not inherit write access nobody decided to give it. It runs `node scripts/build-snapshot.mjs "$RUNNER_TEMP/snapshot.txt"` with **no `npm ci`** — the script imports `public/js/parse.js`, `public/js/snapshot.js`, `public/js/sources.js` and node builtins, nothing else — then force-pushes that file **and its `.sha256` sidecar** to the orphan branch `snapshot` from a throwaway `git init` in `$RUNNER_TEMP`, so the published branch cannot pick up a stray working-tree file and every push is exactly one commit. Deliberately **no `push` trigger**: the snapshot is a function of the 17 remote lists, not of this repository's contents. The checkout uses `persist-credentials: false` because the push carries its own token. The script exits non-zero if any source is non-200, yields no parseable link, or has drifted past its band — a silently wrong snapshot is worse than a red run. **Every action in all three workflows is pinned by SHA** with its version in a trailing comment, for the same reason `release.yml` pins its reusable workflow: this job holds a write token, and a `v4` tag is repointable by whoever owns the action. `tests/unit/workflows.test.js` guards the trigger shape, the job-scoped permission, the SHA pinning across all three files, the paired publish of snapshot + checksum, and the `branches-ignore` above. It also guards the three invariants that are one token wide and fail silently: that the nightly build command carries **no `--write-baseline`** (which would set `baseline = null`, skip `checkDrift` entirely and rewrite `snapshot-baseline.json` from the very run that should have been refused — every other gate green throughout), that `test.yml` still runs `test:coverage:ci` **and** that script still carries both `=100` thresholds, and that no workflow interpolates `github.ref_name`/`head_ref`/`event` into a `run:` block rather than passing it through `env:`.
- `.github/workflows/release.yml` — triggered by `push` of a `v*` tag. The `build` job first `curl --fail`s `snapshot/snapshot.txt` **and `snapshot/snapshot.txt.sha256`** off the orphan branch, runs `sha256sum -c` on them, and only then copies the file into `public/data/snapshot.txt` — **before** the compiler runs, because `//go:embed` reads the working tree, so a release built without that step ships the committed placeholder. `--fail` is what turns a deleted branch or a renamed file into a red job; without it curl saves the 404 body and exits 0. `set -euo pipefail` is what makes a failed `sha256sum -c` stop the step at all — without it the script runs on to the copy and the release ships anyway. The checksum attests that what ships is what the nightly job produced; it is **not** a signature and says nothing about whether the 17 upstream sources were honest, which is the drift guard's job. Nothing is committed back; the overwrite lives in the runner's checkout. It then cross-compiles 5 platforms (windows/linux/darwin × amd64/arm64, `CGO_ENABLED=0`) and injects `-X main.version=<tag>` — **through `env: REF_NAME`, never `${{ github.ref_name }}` inside the `run:` block.** A `${{ }}` expression is substituted into the script before bash parses it, and `git check-ref-format` permits `$`, backticks, `;` and `&` in a tag, so interpolated, a tag named `v1$(…)` is command substitution running on the runner that builds every published binary. For the same reason `contents: write` is **on the `release` job, not the workflow** (the `build` job is `contents: read`), so the shell that handles the tag holds no token — the rule `snapshot.yml` already followed. Publishing is **not** in this repo: the `release` job calls the reusable `rahgozar94725/release-workflows/.github/workflows/release.yml`, **pinned by SHA** (`e17e401`, v2.0.0) rather than by tag, so a moving ref cannot repoint this project at unreviewed code — keep it pinned. Release notes come from git-cliff over `cliff.toml` at the tag being built, not from a raw `git log` range.

## Architecture

Single-process Go server (`main.go`, ~640 lines) + vanilla-JS frontend embedded into the binary. No build step for the frontend, no framework, no TypeScript.

**Backend — four endpoints, all wrapped in `recoverMiddleware(sameOriginOnly(…))` (panic → 500 JSON; browser-labelled cross-origin POST → 403 JSON, before the body is read — note the order, so a panic in the guard is still caught):**

**Load-bearing rule: `sameOriginOnly`'s `Host` check comes before the `Origin` comparison and is not decoration.** The `Origin` arm compares against `r.Host`, which is whatever the browser was told to ask for, so on its own it is satisfiable by DNS rebinding: a page served from `evil.test:3000` whose name is then repointed at `127.0.0.1` sends `Host: evil.test:3000`, a matching `Origin` and `Sec-Fetch-Site: same-origin` — internally consistent headers that pass both arms, with the responses coming back **readable** because the browser now believes it is same-origin. That turns `/check` into an accurate port scanner over the victim's loopback and LAN and hands `/fetch-sources`' bodies back. `allowedHosts` is built in `main()` by `hostAllowlist(addr)` from the address actually bound, and pinning `Host` to it is what makes the `Origin` comparison mean anything. Only a **loopback** bind yields a list (all three spellings — `127.0.0.1:port`, `localhost:port`, `[::1]:port` — regardless of which one `HOST` used, since a user typing `localhost` reaches the same server, **plus the bound address itself**, lowercased: 127/8 is loopback in its entirety, so `HOST=127.0.0.2` binds, passes `shouldOpenBrowser` and gets a browser opened at it, and without its own entry every POST from that page 403s while the map stays non-empty and the `WARNING` line never fires — the app loads and is completely dead); a non-loopback bind has no name this process can know, so the list is empty, **the check is off**, and `main()` logs one `WARNING` line saying so rather than leaving it to be inferred. An empty map must keep reading as *off* and never as *allow nothing*, which would 403 every request on the supported `HOST=0.0.0.0` deployment — `TestOriginGuardSkipsTheHostCheckWithoutAnAllowlist` pins that direction, `TestEndpointsRejectARebindingHost` the other. Mutation-checked: deleting the check fails the rebinding test on all four endpoints. `allowedHosts` is nil in every test that does not install one, which is what keeps the rest of `handlers_test.go` (whose requests carry `Host: example.com`) unaffected.
- `POST /check` — one proxy, returns `{ok, ping?}`. The supported scripting endpoint, documented in the READMEs' HTTP API section.
- `POST /check-batch` — **deprecated, removal planned for a future release**: answers with `Deprecation: true` + `Link` headers and logs a warning per hit. JSON array in, array out. Two strict phases with a barrier between them: all TCP pre-checks finish (`tcpWg.Wait()`), *then* MTProto checks run on survivors.
- `POST /check-stream` — SSE, the only endpoint the UI actually calls. Per-proxy goroutine does TCP check then MTProto check inline (no barrier), emitting `event: progress` per result and `event: done` at the end. Writes are serialized by `mu` because `http.ResponseWriter` is not concurrency-safe.
- `POST /fetch-sources` — `{urls: [...], socks5?: {addr, user?, pass?}}` in, `text/plain` out: the sources' raw bodies concatenated **by request index**, not by who answered first. The page cannot fetch these lists itself (no CORS on `raw.githubusercontent.com`, and the browser sits on the network that made the tool necessary), so the server does it. Sources are fetched concurrently; a source that fails contributes nothing and aborts nothing, so an **empty 200 body is a real answer** and the client treats it as one. Wrong method → 405, malformed JSON → 400, more than `maxSources` (20) urls → 413, an unusable `socks5` config → 400.

**`/fetch-sources` SSRF rules — the server fetches attacker-chosen URLs, and `HOST=0.0.0.0` is a supported deployment with no auth.** Five rules, all in `main.go`:
- **Scheme allowlist** (`checkSourceURL`): `https` only, except `http` when the fetch is routed through SOCKS5 — the one case where the bytes do not cross the server's own network in the clear.
- **Resolve-then-check, never string matching on the hostname.** For the direct client the destination check is the dialer's `Control` hook, which runs *after* DNS resolution and *before* the connection, so there is no window in which a rebinding answer can slip through. `blockedSourceIP` is the `net.IP` predicates (loopback, private, unspecified, link-local, multicast) **plus `blockedSourceNets`**, a CIDR list, because the predicates alone leave real holes: `IsPrivate` knows 10/8, 172.16/12, 192.168/16 and fc00::/7 and nothing else. The list adds `100.64.0.0/10` (**Tailscale gives every peer a 100.x address** and puts MagicDNS on 100.100.100.100), `::/96` (v4-compatible IPv6 — `::127.0.0.1` is 16 bytes, so `To4` is nil and `IsLoopback` is false), the NAT64 prefixes `64:ff9b::/96` and `64:ff9b:1::/48`, `2002::/16` (6to4) and `2001::/32` (Teredo), `fec0::/10`, and the reserved v4 ranges `0/8`, `192.0.0.0/24`, `198.18.0.0/15`, `240.0.0.0/4`. v4-mapped addresses are `Unmap`ped before the match, which is why `::ffff:0:0/96` is deliberately **absent** — a row for it would block every mapped address including public ones. `TestBlockedSourceIPCoversTheReservedRanges` is the table, and its `want=false` rows are what stop the list from being widened into blocking real sources.
- **Redirects are checked on every hop.** Each hop dials again, so the `Control` hook covers the destination half; `CheckRedirect` covers the scheme half and stops at 10 hops. On the SOCKS5 client `CheckRedirect` additionally **requires the hop's scheme to equal `via[0]`'s**: that leg accepts plain HTTP, so without it an `https://` source could answer `302 Location: http://…` and have its body cross everything past the proxy — for Tor, the exit node — in the clear, which is a list-rewriting position over a URL the user believes is TLS-protected. `http` is allowed there only for a URL the user typed that way.
- **Size and time are bounded while reading, per source *and* per request.** `io.LimitReader(body, maxSourceBytes+1)` with `maxSourceBytes = 1 MiB` caps one source; the read also passes through a `budgetReader` charging a `byteBudget` of `maxRequestSourceBytes` (4 MiB) that all of one request's sources **share**, because the handler buffers every source whole until the last one lands — so the per-source cap alone would allow `maxSources` × `maxSourceBytes` resident. `maxFetchSourcesInFlight` (4) then caps how many requests hold a budget at once, via `fetchSourcesSlots`, a package-level buffered channel the handler acquires **before** reading the body and releases on the way out; a caller that goes away while queued takes its request with it. `sourceTimeout` (30 s, a `var` only so the test can shorten it) bounds each attempt — a source that also retries through SOCKS5 can therefore cost up to two of them.
- **The SOCKS5 path checks the destination *before* dialling the proxy** (`checkSOCKS5Destination`), since there is no dial hook to hang it on: a literal address is judged directly, and a name is judged whenever this machine can resolve it. A name only the proxy can resolve is left to the proxy — that is the case the feature exists for. **It resolves through `net.Resolver` directly and deliberately not through `cachedLookupHost`** — `dnsCache` is written by `tcpCheck` from a hostname any `/check` caller supplies and pinned for 5 minutes whatever the record's TTL says, so reading it here would let a caller seed an allowed answer for a name they control and then repoint it, while the proxy resolves the name again at connect time. The direct path has no such window because its check is the dial hook. Costs at most `maxSources` lookups per request. The fail-open on a resolution error is the load-bearing half and is pinned in both directions by `TestCheckSOCKS5DestinationAllowsANameItCannotResolve`. **Accepted residual:** the proxy address itself is caller-supplied and dialled unchecked, a bounded forgery primitive (SOCKS5 handshake bytes at an arbitrary `host:port`); blocking loopback there would block the local Tor/tunnel proxies this exists to use.
- `allowPlainHTTPSources` and `allowedSourceIP` are test seams and nothing else — `false`/`nil` in production, written only by `fetchsources_test.go`, because every hermetic upstream is plain HTTP on `127.0.0.1`, which is exactly what the policy rejects. `allowedSourceIP` exempts individual addresses rather than switching the check off, so a test that exempts loopback still proves `10.0.0.1` is blocked.

**Request limits:** every handler caps the body at `maxBodySize` (8 MiB) via `http.MaxBytesReader`; the two batch endpoints additionally reject more than `maxBatchSize` (10 000) entries. Either violation answers `413` with `{"error": …}` — shared logic in `readCheckRequests`, which `/check-stream` runs *before* committing to SSE so a rejected request gets plain JSON, not an empty event stream. Note the UI posts the whole pasted list in one request, so a pasted list over 10 000 entries now fails with the generic error toast.

`public/` is baked in with `//go:embed public` + `fs.Sub` and served by `http.FileServer` at `/`. Nothing is read from disk at runtime — editing `public/` requires a rebuild (or `go run .`) to take effect.

**Startup** logs the version (`-ldflags -X main.version=<tag>` in releases, `"dev"` otherwise), binds explicitly with `net.Listen` (bind failure dies before any browser launch), then opens the local browser at the bound address — only when the bound host is loopback (`shouldOpenBrowser`); `NO_BROWSER` set to any non-empty value suppresses it, and a non-loopback `HOST` suppresses it automatically. The launcher (`browserCommand`: `rundll32`/`open`/`xdg-open`) is fire-and-forget; a failed launch logs one line and never affects the server.

**Proxy verification** (`checkProxy`) is a real MTProto handshake, not a TCP ping: `dcs.MTProxy(addr, secret)` resolver → `telegram.NewClient` with public test creds (`testAppID = 6`, `testAppHash = "eb06d4…"`, hardcoded in `main.go`, intentionally public — no login required) → `help.getNearestDC`. Round-trip time of that call is the reported ping. It carries its own `recover()` in addition to the middleware's; the reason is not recorded anywhere in the repo.

**Load-bearing rule: the `checkCtx.Err()` check after `client.Run` is not redundant — do not delete it.** `gotd`'s `Client.Run` ends with `if err := g.Wait(); !errors.Is(err, context.Canceled) { return err }; return nil`, swallowing `context.Canceled` on purpose because that is how it signals a normal shutdown once the callback returns. Without the explicit check, a `checkProxy` whose parent context is cancelled returns `(0, nil)` and every caller reads that as a working proxy with a 0 ms ping — the trigger being a client disconnect, including the UI's pause and stop, which `abort()` the fetch. `DeadlineExceeded` was never affected, so the `/check-stream` hard `t+10s` context always reported correctly. Testing `checkCtx` rather than `ctx` is deliberate and safe: `g.Cancel()` on the success path cancels `tdsync.NewCancellableGroup`'s own derived context, not `checkCtx`, so a real ping still gets through. `TestCheckProxyReportsConnectionFailures/context_already_cancelled` guards the check itself, and `TestCheckProxySucceedsAgainstAWorkingProxy` guards the other half — that a completed handshake still returns its ping. That success test was originally written *because* this reasoning was only read off `gotd`'s source; it is now exercised against a fake proxy, though still never against real Telegram.

**`checkOptionsHook` is a test seam and nothing else.** A `func(*telegram.Options)` applied at the end of `newCheckOptions`, nil in production. `checkproxy_test.go` is the only thing that sets it, for the two things the fake-proxy test cannot do without: trusting the fake server's RSA key instead of Telegram's key list, and widening `ExchangeTimeout` past the production 2s, which is a budget for a remote proxy and not for a server doing DH on the same CPU as the client. It is deliberately *not* a place to swap `SessionStorage` — see the `sharedSession` rule above.

`decodeSecret` tries the raw input and then a junk-right-trimmed copy (the trim set overlaps the base64 alphabets, so raw must come first); per candidate it tries hex first (both candidates), then base64 RawURL → URL → RawStd → Std. Known limitation: a base64 secret whose last character is `+`, `/` or `_` *and* is followed by junk still decodes to the wrong bytes — the raw pass fails on the junk, and the trim pass strips that final alphabet character along with it.

**Load-bearing rule: `sharedSession` is one `session.StorageMemory` shared across all checks — do not change it to per-check storage.** It reads like a bug (package-level mutable state shared across concurrent goroutines) and was "fixed" once on exactly that theory (d0288be); the fix destroyed detection. Measured 2026-07-23, same 1022-proxy input, concurrency 50, timeout 10s: per-check sessions → **0/1022 working in 98s**; reverting only the storage line → **99/1022 in 74s** (pings from 133ms). A same-binary control later scored 0/1022 in a throttle-poisoned slot, confirming the slot effect and that the delta is the storage line, not network luck — and run order worked *against* the shared variant (it ran in the dirtier slot and still won). Those numbers are the fact; the mechanism is inferred, not instrumented: with a shared session the first successful check negotiates the auth key and every later check reuses it, skipping the DH exchange that otherwise must fit inside the 2s `ExchangeTimeout` — which is also how a real Telegram client behaves — and each fresh key creation counts against the source IP, so per-check sessions make every scan degrade the next (self-poisoning; the "N found on first run, zero after" signature). If the real mechanism turns out different, the rule stands on the numbers. Never measured in a clean slot: per-request sharing (logically identical within one scan; **the variant worth revisiting** — if it matches, it restores isolation between scans as a small commit) and a longer `ExchangeTimeout` (1/1022 in a moderately poisoned slot — suggestive of insufficient, not proven). `TestNewCheckOptionsSharedSession` guards the sharing.

**Shared mutable state to be careful with:**
- `dnsCache` — `map[string]*dnsCacheEntry` behind `dnsCacheMu`, 5-min TTL, consulted by `tcpCheck` before dialing. Written from a fully caller-supplied hostname and ignoring the record's own TTL, which is why no SSRF check may read it — see the `checkSOCKS5Destination` rule above.

**Timeout layering** (four levels, don't collapse them): UI-selected `timeout` clamped to 3–30s (`defaultTimeout = 5`) bounds the gotd context; `/check-stream` wraps that in a hard `t+10s` context so a stuck proxy can never wedge a goroutine; `tcpTimeout` is a fixed 1.5s dial; the client also arms its own `(timeout+30)*1000 + 120000` ms abort on the whole stream. Server `WriteTimeout` is 300s to keep long SSE streams alive; shutdown is `SIGINT`/`SIGTERM` → `srv.Shutdown` with a 5s context.

**Concurrency** comes from the `X-Concurrency` request header, clamped to `[1, maxConcurrency = 50]`, enforced by a buffered-channel semaphore. Note the server's own fallback when the header is absent is `10`, while the UI's default selection is `50`.

**Frontend** — nine ES modules under `public/js/`, no bundler and still no build step. `public/index.html` loads exactly one of them, `<script type="module" src="/js/app.js">`; the browser fetches the rest. Module scripts are deferred, so a small inline script in `<head>` applies the persisted `data-theme`, `dir` and `lang` before CSS paints — without it a light-theme or LTR user gets a dark/RTL flash. It carries its own copy of the locale list (`fa`/`en`/`ru`/`zh`) because it runs before the module graph exists and cannot import `i18n.js`, so **adding a locale means editing `index.html` too** — otherwise an unknown stored `lang` paints LTR and `resolveLang()` flips it to RTL a moment later. `tests/unit/boot.test.js` runs that script against stub globals.

- `i18n.js` holds all four locales (fa RTL default, en, ru, zh); DOM text is bound via `[data-i18n]` attributes and applied in `setLanguage()`. Adding UI text means adding the key to **all four** locales. The old `status` key is gone — there is no single status line anymore.
- Layout is a single-column flow, not the old two-textarea grid: settings bar → four stat tiles (`#tileChecked`/`#tileTotal`, `#tileWorking`, `#tileBest`, `#tileFailed`/`#tileSkipped`, all written by `renderStats()`) → progress bar → input section → results panel → console drawer.
- The input section's `.io-pane` holds `#inputProxies` plus an absolutely-positioned `.empty-hint` overlay (icon, localized copy, an example `tg://` link) shown only while the textarea is empty (`:placeholder-shown`). During a scan, `body.scanning` (toggled by `setScanUI()`) hides the pane entirely and shows `#inputSummary` instead — a localized "N links loaded · M skipped" line written by `updateScanSummary()`. Stop restores the pane (`setScanUI(false)`); pause deliberately does not — `togglePause()` never calls `setScanUI()`, so the input stays collapsed through a pause since `scanState` remains `'scanning'`. The server has no notion of this collapse.
- Results panel: `workingProxies` (`{link, ping, server, port}`) is the sole source of truth, populated from SSE `progress` events in `runCheckStream()`. `renderResultsTable()` — always rebuilt with `createElement`/`textContent`, never `innerHTML`, since server/port are attacker-controlled strings from pasted URLs — is the default view; `#resultsPanel[data-view]` toggles between it and a plain-text `#outputProxies` textarea via the `.view-toggle` Table/Plain-text buttons (`setResultsView()`). Rendering is coalesced through `scheduleResultsRender()` (one `requestAnimationFrame` per burst) rather than re-rendering per SSE event. Per-row copy is wired as **one delegated `click` listener on `#resultsBody`** (`btn.dataset.index` → `workingProxies[i]`), justified by rows being rebuilt wholesale on every render. All copy/export paths read `workingProxies`, never the DOM, and every artifact preserves the secret-bearing `p.link`; `proxyLine(p)` (`link + ' # Ping: Nms'`) formats the text artifacts — `exportResults('json')` builds `{link, ping}` objects directly instead.
- Scan lifecycle is two independent flags: `scanState` (`'idle'`/`'scanning'`, drives the start button flipping to a red Stop via `updateStartBtn()`) and `isPaused`. Both pause and stop call `controller.abort()` on the in-flight SSE fetch — pause differs only in that resume re-POSTs `/check-stream` with the proxies missing from the `checkedKeys` Set (keys are `server:port:secret`). The server has no pause concept.
- `parseLink()` sanitizes client-side before anything is sent: fixes `.&` typos, requires a scheme, rejects ports outside 1–65535, drops spam secrets (>170 chars or containing a long `AAAA…` run). Dedup by `server:port:secret` happens in `startCheck()`.
- **Snapshot line grammar — there is no space before the `#`, and that is load-bearing.** `scripts/build-snapshot.mjs` writes, and `snapshot.js` reads:

  ```
  # generated <ISO8601> by scripts/build-snapshot.mjs
  # 0 iwh3n/tg-proxy/refs/heads/main/proxys/All_Proxys.txt
  # 1 Argh94/Proxy-List/main/MTProto.txt
  tg://proxy?server=…&port=443&secret=ee00…dd#seen=1;src=8
  ```

  `new URL().search` ends at `#`, so a space before it lands *inside* the last parameter value: every line would yield a secret with a trailing space — a different `proxyKey`, and a secret the server only rescues through `decodeSecret`'s junk-trim path. Both the original one-pager and Phase 0's `measure.mjs` emitted that space; the format does not. Unit tests on both sides pin it. Since `splitFragment` runs before every parse, a space-padded line coming *in* no longer produces that secret — but the rule on what this repo **writes** stands, because nothing guarantees the reader is this page. The same reasoning runs the other way at write time: a **source-side** comment fragment (`…secret=ee00# MTProto EU (100)`, which really occurs in the corpus) is stripped *before* the line is parsed, not after — stripping afterwards leaves the collected key holding a padded secret while the emitted line holds the bare one. Every emitted line therefore carries exactly one `#`.
- **No `#` fragment may reach an export — not the snapshot's `#seen=…;src=…`, and not a source-side comment either.** `parseLink()` sets `proxy.original` to the whole cleaned line, which flows `globalLinkMap` → `workingProxies[].link` → clipboard, TXT and JSON, so anything left on the line is copied back out. `snapshot.js` exports `splitFragment(line)` as the single definition of where a link ends, and all four readers use it: `parseSnapshot()` (which returns fragment-free links, attribution coming back separately as `Map<proxyKey, {seen, srcs}>`), `scripts/build-snapshot.mjs` when it collects the corpus, `loadUserSources()`, and `startCheck()` via `stripFragments()` — the last one being what covers the paste, the file picker and the drop target, since all three write to the same textarea and third-party lists really do carry `…&secret=ee00# MTProto EU (100)`. Stripping is deliberately **not** in `parse.js`, whose behaviour is pinned by the pre-refactor golden baseline; nothing is lost by that, since `new URL()` already ends the query at the `#` and server/port/secret were always read off the bare link. Tests assert the *artifact*, not the intent.
- **Load-list flow** (`loadSnapshot`), in this order, each step total — a failure is logged and the next still runs: (1) `POST /fetch-sources` with the single `SNAPSHOT_SOURCE_URL` (the nightly orphan branch), logged **plainly** on failure because a network the server cannot cross is the case the feature exists for and the drawer should not fly open for it; (2) `GET /data/snapshot.txt`, the baked copy, logged as an **error** if that also fails; (3) `POST /fetch-sources` with the user's own enabled sources, **chunked to `MAX_SOURCES_PER_REQUEST`** (which mirrors `maxSources` in `main.go`, guarded by `sources.test.js` because nothing else ties the two files together) and posted one batch at a time — an error too, since nothing else covers their list, and a batch that fails costs its own sources and no others rather than dropping the whole step to one 413. Only **user-added** sources are fetched: the built-ins are what the nightly snapshot is *made of*, so fetching them would only duplicate it. Snapshot links and user links are deduped through `parseProxyList` as **one** list rather than concatenated. A load that yields nothing leaves the textarea alone — a failed load must not cost the user a paste they already made.
- **The snapshot's sources are third-party and unpinned, and the drift guard is what stands in for trust.** The 17 lists are fetched by mutable branch ref, and the result is force-pushed to a branch that every release embeds and every user loads with one click — so a takeover of any one of them (several are single-maintainer repos) is a position to put attacker-operated proxies in front of everyone, and "it parsed" proves nothing. Pinning each source to a commit SHA is the textbook fix and is **not available here**: these files are rewritten daily, and pinning them freezes the freshness the nightly rebuild exists to deliver. So `buildSnapshot` fails closed on volume instead, against per-source counts committed in `scripts/snapshot-baseline.json`: a source outside `driftBand` (`×2 + 20` up, `/2 − 20` down — a tripwire for a flood, not a linter for daily variation) reds the run until a human looks. The baseline also carries each source's **url at its position**, so reordering `DEFAULT_SOURCES` without a deliberate bump fails too — `src=` ids are positional, and a reorder silently re-attributes every line of every snapshot ever published. Regenerating is a deliberate act (`--write-baseline`, which skips the guard for that run) and must never be what CI does. **Known residual, not small:** a source whose contents are *replaced* at constant volume passes; catching that needs a churn comparison against the previous snapshot, which is a separate change. The `.sha256` sidecar is a different guarantee entirely — it attests the release embeds the file the nightly job produced, not that the sources were honest.
- `sources.js` is keyed by **url**, never by index, because a nightly rebuild may reorder sources and an index-keyed model would silently repoint a score. The **`src=` ids in the snapshot are positions in `DEFAULT_SOURCES`**, so appending to that array is safe and reordering it is not — and `scripts/build-snapshot.mjs` imports the array from this module rather than keeping a copy, since two lists that drifted apart would misattribute every line. `parseSources()` is total for the same reason `resolveLang()` is: its input is an origin-keyed `localStorage` value on `127.0.0.1:3000` that any other local dev server could have written, and a throw at module scope would take the whole page's event wiring with it. It also applies `isValidSourceUrl` on the way in, not only `addSource` on the way from the field: a stored url without a scheme survives `shortUrl()` unchanged and therefore **collides with the built-in it shortens to**, so disabling that phantom row would drop the real built-in's links from the next load while its own row still read enabled. Both sides also **normalize** (`normalizeSourceUrl`, reassembled from `new URL()`'s parts rather than read off `.href`, which keeps a trailing `?`/`#`) for the other half of the same problem — the dedupe and `shortUrl()` are exact string comparisons, so `HTTPS://RAW.…`, `…:443/…` and `…txt#` would each be fetched again and scored as a source of their own. The **scheme** is deliberately not normalized: `http://` and `https://` of one path are different fetches under the server's policy, so adding the http variant of a built-in really does make a second source. Credentials in the url are refused outright rather than stripped, since this value is persisted in `localStorage` and posted to `/fetch-sources` on every load. **One-time cost, undocumented anywhere else:** a stored url that fails the new validation is dropped on the next boot, taking its accumulated score with it, with no log line — a second irreversible action beside restore-defaults, though one that can only fire on a list written before this change.
- Disabling a source drops its links from the **load** as well as from ranking (`dropDisabledSources`), but only when *every* source that published a proxy is disabled; an unattributed proxy, an undeclared `src=` id and a header url the model does not know are all kept. It is applied at load time only — after that the textarea is the truth, and a source toggled off later does not reach back into a list the user is looking at.
- Scan order is **descending `seen`, then descending source score** (`orderForScan`), applied where the request body is built so file order still equals scan order on the server. The `seen` direction is measured, and it has been measured in both directions — see [docs/adr/0001-proxy-source-snapshot.md](docs/adr/0001-proxy-source-snapshot.md) before changing it.
- The SOCKS5 address and credentials persist in `localStorage` like the other settings (`socks5Addr`/`socks5User`/`socks5Pass`) and ride **both** fetch steps. An empty address sends no `socks5` field at all, which is what the server already reads as direct-only. The password is stored in plaintext — there is nowhere better, the page has no backend session — so the UI says so in all four locales (`socks5Warning`).
- **Accessibility of the two things the page says without moving focus.** `#toast` and `#snapshotMeta` both carry `role="status" aria-live="polite"`, and `showToast()` sets the `show` class *before* the text and clears the text when it hides — `.toast` is `visibility: hidden` until then, and a hidden subtree is outside the accessibility tree, so writing the message first would mutate a region nothing is watching. `toastSourceInvalid` is the case that forced it: unannounced, a refused url is indistinguishable from a dead button. **Known gap, not a small one:** this covers two elements, not everything the page reports. Every activity-log line (a 413 on one batch of user sources, a snapshot step that failed while another succeeded, the duplicate count), the drawer force-opening itself, `#inputSummary`, the four stat tiles and the results table are all still visual-only. `#sourceUrlInput` is named by `aria-label` rather than the `<label for>` the SOCKS5 fields below it use, because `.sources-add` is a single flex row of input + two buttons; `setLanguage()` rewrites the label and the placeholder together, and `lifecycle.test.js` also pins the static value in `index.html` to `translations.fa.sourceUrlPlaceholder`, since a top-level throw in `app.js` skips `setLanguage()` and leaves the markup's value as the field's only name.
- Restore-defaults is the only irreversible control on the page and the only one that asks (`confirm`, `confirmRestore` in all four locales). jsdom implements no `confirm` at all, so unstubbed it answers `undefined` and silently cancels; Playwright dismisses an unhandled dialog, which is what makes the first click in `controls.spec.js` a real cancel test.
- The console (`#console`) now lives inside `<details id="consoleDrawer">` — collapsed by default, auto-opened by `log()` whenever a line is logged with `kind === true || 'error'` (`drawer.open = true`), so scan/parse errors surface without the user having to expand it manually.
- Every handler is wired with `addEventListener` inside `app.js`; `index.html` carries zero `onclick`/`onchange` attributes and `app.js` leaks no function to `window`. The wiring is by ID, so **renaming or removing an ID in `index.html` silently unwires that control** — `tests/e2e/controls.spec.js` exists to catch exactly that.
- **Load-bearing rule: in `app.js`, every `addEventListener` runs before the first paint call.** The file ends with the wiring block and then `setLanguage`/`setTheme`/`updateStartBtn`/`loadSettings`/`syncSoundUI` — that order, not the reverse. `app.js` is an ES module, so a top-level throw aborts evaluation and everything after it is skipped; with painting first, one bad value left the page rendered normally with all eleven controls dead and nothing in the console. (The classic `script.js` this replaced was immune: its function declarations landed on `window`, so the inline `onclick` attributes kept working through the same throw.) For the same reason the prelude's only outside input is total — `readStored`/`writeStored`/`removeStored` swallow a denied `localStorage`, and `resolveLang()` falls back to `fa`, which is what keeps all thirteen `translations[currentLang]` lookups in the file safe. `localStorage` is origin-keyed and this app lives on `127.0.0.1:3000`, so a foreign `lang` value written by another local dev server is the realistic trigger. `tests/unit/boot.test.js` guards both halves, including a source-order assertion.
- CSS is split by concern and must stay that way: `tokens.css` (custom properties) → `base.css` (reset/typography) → `components.css`. Theme is `[data-theme]` on `<html>` (default `'dark'`), persisted in `localStorage` alongside language and the finish-sound toggle. The `localStorage` entry only persists the preference — the completion beep fires in `finish()`, and only when the checkbox is currently checked.
- Two deliberate button systems in `components.css` — do not "unify" them: action buttons (start/pause/stop/copy/export/file/load) are 48px glassmorphism (`backdrop-filter: blur(8px)`, glass borders/inset shadows) with gradient fills — start blue→indigo, copy/export emerald, pause amber, stop red, load-list violet, file the same blue→indigo as start but dimmed to 0.75 alpha; header controls (theme/sound/language/help) are a separate flat 34px system. `.rowcopy` and `.view-toggle` are a third thing, table chrome deliberately outside both systems — flat, bordered, no backdrop-filter, sized to sit inside table rows and the results-head toolbar. **`.btn-load` is deliberately not a peer of `.btn-file`** and must not be folded back into its rules: it is violet at full strength and shares `flex: 2` with start/stop/copy, because the staleness measurement behind the baked snapshot (a 23-hour-old list works at 38.6 %/35.4 % against 39.2 % for a same-minute build) makes loading the built-in list a headline action rather than a fallback. `tests/e2e/prominence.spec.js` reads both computed styles in both themes and fails if they converge again.
- The `<h1>` title wraps an `<a>` linking to the GitHub repo.
- Zero CDN at runtime: Vazirmatn (Persian) + Inter (Latin) woff2 are self-hosted under `public/fonts/`.

**Go tests** — `main_test.go` (units: `decodeSecret`, `resolveAddr`, `hostAllowlist`, `shouldOpenBrowser`, `browserCommand`, `readCheckRequests`, the shared-session guard), `handlers_test.go` (the HTTP surface), `checkproxy_test.go` (`checkProxy`'s failure paths), `fetchsources_test.go` (`/fetch-sources`, incl. every SSRF rejection path), `proxytest_test.go` (live handshake, skips without `testdata/proxies.txt`), and the `race_test.go`/`norace_test.go` pair, which is nothing but `raceTimeoutFactor` behind `//go:build race` and its negation.

**`raceTimeoutFactor` is why the CI race step is not a coin flip.** `checkproxy_test.go` asserts wall-clock budgets, and under `-race` the fake proxy does its RSA and DH on the same CPU as the client: instrumented, the 20 s success budget was overrun on a loaded machine **with no `DATA RACE` reported at all**, i.e. pure overhead. The factor multiplies every wall-clock ceiling the race step drives — the success test's `timeoutSec`, the stall test's 3 s, the cancelled-context test's 500 ms, and `fetchsources_test.go`'s two — and is 1 in an ordinary build, so the normal run keeps asserting the tight numbers — the ones that would catch a real regression in how long a check takes. It is 8 rather than the 4 that measured sufficient here because a two-core runner is slower than this machine and one failure at 4 was seen and never reproduced; the only cost is how long a genuinely hung test takes to give up.

- `newMux()` exists as the test seam: `main()` used to build the mux and close over `recoverMiddleware` as a local, which made both unreachable from a test. Both are package-level now and `main()` holds only the server, signals and browser launch. Keep it that way — an endpoint added straight into `main()` is an endpoint no test can reach.
- `handlers_test.go` is **hermetic**: every request either fails before `checkProxy` (wrong method, bad JSON, oversized body, too many entries) or carries an empty list, which runs zero checks. Nothing in it dials, so it needs no `-short` guard.
- `checkproxy_test.go` is hermetic for the same reason and by the same rule: the network tests bind `127.0.0.1:0` and talk to a listener the test owns, so nothing dials off-box and the file carries no `-short` guard. It covers the two argument-validation errors (`decode secret`, `create MTProxy resolver` — short secret and unknown codec tag), a closed port, a listener that hangs up before the obfuscated2 handshake, an already-cancelled context (the guard on the `checkCtx.Err()` rule above), and a listener that accepts and then goes silent, which is what proves the `timeoutSec` context actually bounds the call. The stall test asserts a *window*, not just an upper bound: returning before the timeout would mean the connection died for some other reason and the timeout was never measured. Its lower bound is deliberately **not** scaled by `raceTimeoutFactor` — that half is what proves the timeout fired at all, and it costs nothing under instrumentation. Mutation-checked: swallowing the `client.Run` error fails both connection tests, and switching the context timeout from seconds to milliseconds fails the stall test.
- `startFakeProxy` in the same file is the success path, and it is a real handshake — `gotd/td/tgtest`'s MTProto server with `mtproxy/obfuscated2.Accept` in front of it, so the client's own `dcs.MTProxy` resolver does the obfuscation it always does. Three details are load-bearing and were each found by the thing failing without them: the codec must be `codec.NoHeader{Codec: codec.PaddedIntermediate{}}`, because that is what `dcs.MTProxy` picks for a Simple 16-byte secret and the tag travels inside the obfuscated2 header instead of leading the stream; `help.getConfig` must be answered (register `tgtest/services/config`), because gotd sends it during connection setup and an unanswered one kills the connection before `help.getNearestDC` is ever sent; and `sharedSession` must be swapped for a fresh one and restored, or the auth key negotiated against the fake server is handed to `proxytest_test.go`'s live check. The test asserts the auth key landed in the session rather than leaning on the ping, which is 0–3 ms over loopback and would pass even if nothing happened. Mutation-checked by dropping the `checkOptionsHook` application: `key fingerprint not found`. Cost: ~1.1 s and five test-only indirect entries in `go.mod` (`testify`, `go-spew`, `go-difflib`, `yaml.v3`, `nhooyr.io/websocket`) — none of which reach the binary, which is 21.6 MiB.
- It covers the 405s, the `400 {"ok":false}` on malformed JSON, the `413`s from both limits on all three endpoints, `/check-batch`'s `Deprecation`/`Link` headers, that `/check-stream` answers a bad request as plain JSON rather than a committed event stream, that an empty list still produces a terminated `event: done`, and that `/` and `/js/parse.js` come off the embed. The origin guard's own matrix lives here too: both rejected `Sec-Fetch-Site` values, a foreign `Origin`, the six accepted shapes (incl. the headerless scripting path), that the guard runs before the body is read, that `/check-stream` answers 403 as plain JSON, and — via `postFromHost`, which sets `req.Host` because a `Host` *header* does nothing in Go — the three `Host` cases from the rule above. Mutation-checked: dropping the `Deprecation` header, removing the 500 from `recoverMiddleware`, and adding a `flusher.Flush()` before validation each fail exactly one test. Note that merely *setting* the SSE header early is not a bug and does not fail anything — `jsonResponse` overwrites it, since nothing is sent until the first write.
- `fetchsources_test.go` is hermetic by the same rule — every upstream is an `httptest` server on `127.0.0.1`, reached only through the two test seams. It covers the shape (405, 400, 413 on both limits), concatenation in request order, a failing source contributing nothing, the per-source timeout, and one test per SSRF rejection path: plain HTTP, a non-HTTP scheme, a private destination, a loopback destination, an oversized body, and a redirect into a blocked range. The SOCKS5 leg runs a real local SOCKS5 server and asserts the retry is taken only after the direct attempt fails, that credentials are passed, that a request without a proxy stays direct, that a rejected scheme never reaches the proxy at all, and that the destination and redirect checks apply on that path too. It also carries the `blockedSourceIP` table, the scheme-downgrade redirect test (read off `socks5Client`'s own `CheckRedirect`, since reaching it end to end would need a real TLS upstream), a five-source request proving the shared byte budget bounds the whole request rather than each source, and a `maxFetchSourcesInFlight × 2` concurrent-request test proving the in-flight cap holds. Mutation-checked: dropping `checkSOCKS5Destination` fails the private-destination and redirect tests, dropping the retry fails three, dropping `proxy.Auth` fails the credentials test, dropping `100.64.0.0/10` or the `::/96`+NAT64 rows fails the table, neutering the redirect scheme check fails the downgrade test, bypassing `budgetReader` fails the budget test, and releasing the semaphore slot immediately fails the in-flight test.

**Frontend tests** — `node:test` + jsdom for units, Playwright for e2e. No bundler, no transpiler. `SPEC.md` is the contract this suite was built to; the ESM refactor that made it possible is documented there.

- `tests/unit/` — `parse`, `sse`, `format`, `i18n`, `render`/`state`, `snapshot`, `sources` (all at 100% line and branch), plus `lifecycle.test.js` (full scan against a stubbed `fetch`, and the three Load-list network paths), `boot.test.js` (the boot-order rule above), `build-snapshot.test.js` (the builder, incl. the no-space-before-`#` pin), `data-snapshot.test.js` (the committed placeholder really parses and really is RFC 5737 space), `workflows.test.js` (the YAML rules listed under **Commands**, plus the two halves of the snapshot chain: that `SNAPSHOT_SOURCE_URL`'s branch and filename are what `snapshot.yml` pushes, and that `release.yml` copies the fetched file to the very path `SNAPSHOT_URL` fetches — rename either and every other gate stays green while every released binary serves the placeholder for good), `dom-helper.test.js` (the harness's own shims) and `harness.test.js` (asserts nothing test-related sits under `public/`). `app.js` reads ~35% and stays misattributed: `tests/helpers/dom.js` cache-busts each mount with a `?mount=N` specifier, so every mount is a separate module URL to the coverage reporter.
- `mountApp({ beforeBoot })` runs its callback *before* the jsdom globals are installed, which is the only window in which boot-time conditions can be staged. Denying `localStorage` there means **replacing `window.localStorage` wholesale** — jsdom implements `Storage` as a Proxy whose `defineProperty` trap drops the definition and returns success, so patching a single method reads as working and denies nothing.
- `tests/helpers/dom.js` — mounts the **real** `public/index.html` in jsdom, so a renamed ID fails a test. jsdom cannot run `<script type="module">`, so `app.js` is imported by Node with the jsdom window installed on `globalThis` first. **jsdom has no `innerText`** — the helper defines it in terms of `textContent` before importing `app.js`; without that shim every `log()`/`setLanguage()`/`showToast()` write silently vanishes. `requestAnimationFrame` is replaced with a controllable version so coalesced rendering can be flushed deterministically.
- **Load-bearing rule: inside a mount, never `await` a bare `setTimeout` — import one from `node:timers/promises`.** The helper wraps `window.setTimeout` so every handle is `unref()`d, which is what stops a toast or watchdog timer from holding the test process open past the last assertion, and `setTimeout` is one of its `GLOBAL_KEYS` — so a bare call *inside a mount* gets the unref'd wrapper, and an unref'd timer does not keep the event loop alive. When that wait is the only thing pending, the loop drains and node cancels the awaiting test **and everything queued behind it**. It reports as `cancelled`, not `failed`, so the run is red with **no failing assertion anywhere in the log**: 314 tests, 0 failed, 10 cancelled, every one of them `Promise resolution is still pending but the event loop has already resolved`. `render.test.js`'s two toast waits hit this on CI's Node 22 while passing on Node 26.5 locally — the versions differ in whether anything else holds the loop — and it reproduced across a rerun of the same commit, which is what separated it from a flake. A `node:timers/promises` import is bound before any mount and stays ref'd; the app's own timers stay unref'd, which is the point of the wrapper and costs nothing, since `unref` only means a timer will not hold the loop open by itself.
- `tests/fixtures/golden/parse-baseline.json` — the pre-refactor parser's output over `proxies-dirty.txt`, recorded before any edit and replayed by `parse.test.js`. It is **Node-flavoured**: Node's `URL` accepts `file://localhost?server=…` and Chrome does not, so the same fixture is 227 proxies under `npm test` and 226 in a real browser. `tests/helpers/record-baseline.js` is kept for provenance only — it injects the frontend as a classic script and stopped working the moment `app.js` gained its first `import`.
- `tests/e2e/` — `scan.spec.js` (stubbed `/check-stream` via `page.route()`, plus the Load-list button's three network conditions: a reachable snapshot branch, an unreachable one falling back to the embed, and both failing), `controls.spec.js` (every migrated control, across thirteen specs, zero console errors), `prominence.spec.js` (the `.btn-load`-is-not-`.btn-file` rule above, read off `getComputedStyle` in both themes), `live.spec.js` (skipped unless `E2E_LIVE=1`; the only test that would catch a real server-contract break). ## Known drift and defects (current state — do not "fix" as a side effect)

The READMEs describe intent, and parts have drifted from the code. Verify against source before trusting them. Confirmed by reading the code:

- **No auth and no CORS policy.** The server binds `127.0.0.1:3000` by default (`resolveAddr`); setting `HOST=0.0.0.0` (or a specific address) is the explicit opt-in to wider exposure, and anyone routable can then drive the checker. `PORT` parsing is deliberately lenient (Sscanf error ignored) — preserved behavior, not endorsed design. There **is** an origin check as of this branch — `sameOriginOnly` wraps all four POST handlers in `newMux` — but read it for exactly what it is: a browser control, refusing a request the browser itself labelled `Sec-Fetch-Site: cross-site`/`same-site` or stamped with a foreign `Origin`. An absent pair is allowed on purpose, since `curl` and the documented `POST /check` scripting API send neither, so anything that sets its own headers walks straight past it. It is **not** authentication and is not a reason to keep skipping one. What it does close is the drive-by: `Content-Type: text/plain` is CORS-safelisted, so before it, a plain HTML form on any page the user visited could POST valid JSON here with no preflight and no JavaScript — measured as a three-state port-scan oracle (open 30124 ms, closed 222 ms, filtered 10129 ms) over the victim's loopback and LAN, via `/fetch-sources`' deliberately-unchecked `socks5.addr`. That residual is accepted on the reasoning that the address is the user's own Tor or tunnel, and the guard is what keeps that sentence true — **on a loopback bind only.** The guard deliberately allows a request carrying neither header, so a remote `curl` against a `HOST=0.0.0.0` deployment sails past it and gets the oracle back without a browser at all. Read the accepted residual as scoped to the default deployment; on `0.0.0.0` nothing keeps the sentence true, which is one more thing that deployment opts into.
- **`main_test.go` still tests a parser nobody runs.** It defines and tests its own local `parseProxyLink` helper. The parser that actually runs is `parseLink` in `public/js/parse.js` — now covered at 100% line and branch by `tests/unit/parse.test.js` plus the golden replay, so the coverage gap is closed, but the duplicated Go helper remains and can drift from the JS one without any test noticing.
- **Two Go tests depend on a proxy list that is not in the repo.** `TestBatchParseAndTcpCheck` and `proxytest_test.go`'s `TestTelegramCheckWorkingProxies` read `testdata/proxies.txt` and `t.Skip` when it is absent. The rest run on a fresh clone (`go test . -short -v`: 23 pass, 2 skip as of 2026-08-09), so the earlier "largely a no-op" wording here was wrong. The JS suites have no such dependency — they run from a synthetic fixture.
- **`checkProxy` is covered on a fresh clone, success path included** — `checkproxy_test.go` (see **Go tests** below) runs a full MTProxy handshake against a fake server, so `proxytest_test.go` is no longer the only thing that exercises it. What the live test still uniquely covers is a handshake with *real Telegram*: real keys, real DC, real network. Older entries here claiming no Go test used `httptest`, that the handlers had zero coverage, and that the success path needed a live proxy were true when written and are not any more.
- **The offline Load-list path has never been run on an offline machine.** The embed fallback is covered deterministically by `scan.spec.js` through `page.route()`, and `POST /fetch-sources` was verified against the real snapshot branch (831 lines, header `generated 2026-08-10T04:51:17.982Z`), but no machine was actually taken off the network. Signed off as unmet at Checkpoint D rather than quietly claimed.
- **`app.js` assigns `window.onerror`.** It is the one thing the file puts on `window` and the one handler not wired with `addEventListener` — deliberate, since a global error hook has no element to attach to. Read the "no inline handlers, nothing on `window`" rule above as being about the eleven controls; this line is the exception.

- *Screenshots are stale* — they are not, and the entry had been wrong since `abe2990`. See Repo conventions for how they are taken now.
- *The activity-log drawer opens by itself during a scan* — not reproducible. A clean stubbed scan leaves `#consoleDrawer` closed with six lines logged, and the browser behaviour it was blamed on does not happen either: with the drawer closed, `#console` genuinely overflowing and `scrollTop` moved to the bottom, `details.open` stays `false` (Chromium 151.0.7922.34). Either it was fixed upstream or it was misattributed. Caveat: only bundled Chromium was tested, not the user's own Chrome build.
